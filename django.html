Svelthon · template reference

Django templates, in Svelthon

If you write Django or Flask templates, you already know most of this page. Here is the whole translation — there is not much of it, and nothing to install for it.

  1. An expression is Python.

    {{ x }} becomes {x}, and what goes inside is the Python you would write anywhere else — len(items), x.upper(). No filter language, no restricted subset.

  2. A block is a Svelte block.

    {% if %} becomes {#if}. The # opens, the / closes, the : continues.

The whole mapping

Only the delimiters are coloured below, because they are the only thing that changes. Everything between them is Python you already write.

Autoescaping works the same way in both, which is worth knowing before you go looking for a setting: everything is escaped, and {@html} is the deliberate way out, exactly as |safe is in Django.

The comment row is not the swap it looks like

Svelte has no second kind of comment

In Django the distinction earns its keep: {% comment %} is stripped at render, <!-- … --> is passed through and lands in the page source. That is why {% comment %} exists at all. Svelte has no such split — an authored <!-- … --> is removed from the output, on the server and in the browser alike, so it is the template comment. Only Svelte's own hydration markers survive.

Which leaves the other half of Django's pair with no default: a real comment in the delivered HTML has to be forced, with {@html} or the compiler's preserveComments. Rarely what anyone wants — but worth knowing before you go looking for the setting.

One line of that table has a catch

{@const} is not as free as {% with %}

It must be the immediate child of a block — {#if}, {#each}, {#snippet}, a component — and Svelte refuses it at the top level of a file. Rarely a problem, because the place you reach for {% with %} is usually inside a loop anyway. When it is, the value belongs in the script as a @derived.

A page, side by side

A list with a filter, a counter and an empty state — the template every project writes on its first day.

Django
{% extends "base.html" %}

{% block content %}
<h1>{{ status|default:"All" }} PEPs</h1>

<ul>
  {% for pep in peps %}
    <li>
      {{ forloop.counter }}.
      <a href="{% url 'pep' pep.number %}">PEP {{ pep.number }}</a>
      — {{ pep.title }}
    </li>
  {% empty %}
    <li>Nothing here.</li>
  {% endfor %}
</ul>

<p>{{ peps|length }} shown</p>
{% endblock %}

renders once, to a string

Svelthon
<script lang="python">
peps: list
status: str
</script>

<h1>{status or "All"} PEPs</h1>

<ul>
  {#each peps as pep, i}
    <li>
      {i + 1}.
      <a href="/pep/{pep.number}">PEP {pep.number}</a>
      — {pep.title}
    </li>
  {:else}
    <li>Nothing here.</li>
  {/each}
</ul>

<p>{len(peps)} shown</p>

renders, then keeps running

{% extends %} has no counterpart in the file because layouts are a directory convention: a +layout.svelte beside the page wraps it, with no declaration on either side. The two annotations at the top are what a Django view passed in its context — here they are the component's inputs, and they are ordinary Python annotations. No rune, no decorator.

Where Svelthon does it differently

Template inheritance

Django names a parent and fills its blocks. Svelthon nests by directory: a +layout.svelte wraps every page below it and renders the page with {@render children()}. Layouts nest, so a section can add its own without the pages knowing.

<script lang="python">
children: object
</script>

<header>…</header>
<main>{@render children()}</main>

For a single hole this is about even. For several — Django's named blocks — you pass snippets as props, which is more machinery than {% block %}. It is also more capable, since a snippet takes arguments.

Filters

A Django filter is a small language: {{ x|striptags|truncatewords:20 }}. In Svelthon it is Python, so it is functions and methods — often shorter, sometimes less pretty when it nests. The gain is that there is nothing to learn and nothing to register: any function your module can import, the template can call.

An honest regression

You will miss {% url %}

{% url 'pep' pep.number %} resolves a named route, so renaming a URL does not break templates. SvelteKit has no named routes: you write /pep/{pep.number}, and renaming the directory means grepping for the path. If your project leans on {% url %} heavily, this is the thing you will notice missing.

CSRF

{% csrf_token %} has no equivalent because SvelteKit does not use a token: it compares the request's Origin to the app's own and refuses a cross-site form post. Nothing to write in the form — but the origin must be right, or every POST comes back 403.

What Svelte adds, and Django never needed

A Django template renders once, to a string, and the page is done. A Svelthon template also renders on the server — then keeps running in the browser, and that changes what the syntax has to express.

Keys

{#each rows as row (row.id)} tells Svelte which DOM node belongs to which row, so a reordered list moves nodes instead of rewriting them. Django never needed this, having no DOM to keep. It is optional, and it is the first thing to reach for when a list updates.

Awaiting

{#await rows}…{:then rows}…{:catch e}…{/await} renders the three states of a promise. A Django template has no such thing, because the view resolved everything before rendering.

Reactivity

This is the real difference, and it is not in the template at all. Assign to a module-level name in Python, and everything reading it re-renders.

<script lang="python">
count = 0

def increment():
    global count
    count += 1
</script>

<button onclick={increment}>{count}</button>

No rune, no decorator, no setState. That is the whole feature — and it is why the template can afford to look like Svelte's rather than Django's. The parts that would have been familiar are not where the work is.

Where a Svelthon template is genuinely different

It is not a restricted language

Django deliberately limits templates to keep logic in views. Svelthon does not: {len([p for p in peps if p.year > 2020])} compiles and runs. Whether that is freedom or rope is a matter of taste, and the old advice still applies — a @derived in the script reads better than a comprehension in the markup.

It runs in the browser too

The Python in a component is compiled to JavaScript by Brython at build time and shipped. A +page.server.py stays on the server, exactly as a Django view does. A component does not.

Its data is not a context dict

A Django view returns a context; a Svelthon page declares its inputs as annotations, and a +page.server.py returns them from load(). Same idea, and the names line up.
